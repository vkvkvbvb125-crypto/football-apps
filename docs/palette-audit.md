# 부록 — 확인 방법에 관한 교훈

**RLS가 걸린 테이블의 전수 확인은 앱 경로(anon key)로 하지 않는다. 대시보드 SQL을 쓴다.**

`matches`에 `unique(team_id, match_date)`를 걸기 전, 앱의 anon key + 로그인 세션으로
REST를 조회해 "중복 0"이라고 판단했다. 제약 생성은 실패했다 — 다른 팀에 중복이 있었다.

`matches`의 SELECT 정책은 `is_team_member(team_id)`다. 앱 경로로 조회하면 **내가 속한
팀의 행만** 돌아온다. 없는 게 아니라 안 보이는 것인데 그걸 "없다"로 읽었다.

스키마 전체를 대상으로 하는 검사(중복·정합성·마이그레이션 사전 확인)는 RLS를 우회하는
경로로 해야 한다. 대시보드 SQL Editor 또는 service_role.

# 부록 — 미룬 일: 지역 카드 두 개

팀 설정에 「지역」이 둘이다.

| 카드 | 저장 위치 | 뜻 |
|---|---|---|
| 팀 대표 지역 | `teams.home_place_name` + `home_latitude/longitude` | 날씨 조회용 **좌표** |
| 활동 지역 | `teams.region_code` + `region_label` | 매칭 필터용 **행정구역** |

둘 다 필요하다 — 좌표로는 「같은 구 팀 찾기」를 못 하고, 구/군 코드로는 날씨를 못
부른다. 문제는 총무 눈에 지역 입력이 두 개로 보이고, 카드가 위아래로 붙어 있다는
것이다.

**방향: 「팀 대표 지역」을 「날씨 기준 위치」로 개명한다.**

합치는 쪽은 더 나쁘다. 한 카드에 좌표(지점)와 구/군(행정구역)이 들어가면 단위가 달라
「강남구를 골랐는데 왜 또 장소를 검색하지」가 된다. 이름으로 용도를 구분하는 게 간단하다.

컬럼명(`home_place_name`)은 그대로 둔다 — 표시 이름만 바꾸면 되는 일에 마이그레이션을
붙일 이유가 없다.

# 부록 — 틀린 판단이 주석으로 박히는 것

같은 구조를 두 번 만났다. 둘 다 코드는 정상으로 보였고, 주석이 오히려 그 정상성을
보증하고 있었다.

**1. `TeamSettingsScreen`의 로드 catch**

```ts
} catch {
  // 처음 설정하는 팀이면 team_settings 행이 아예 없을 수 있음 — 기본값 그대로 둔다
}
```

행이 없는 경우는 `fetchTeamSettings`가 `null`을 돌려주지 예외를 던지지 않는다. 즉 이
catch에 들어오는 건 전부 진짜 실패다. 주석이 그걸 「정상 경로」로 설명해 놔서, 삼키는
게 의도된 것처럼 읽혔다. 실제로는 폼이 빈 기본값으로 뜨고 저장 시 계좌가 지워졌다.

**2. `updateTeamProfile`의 전 칸 전송**

```ts
/** 한 번에 보낸다. 필드마다 따로 저장하면 총무가 다섯 번 기다려야 하고,
    중간에 하나가 실패하면 화면과 서버가 갈린다. */
```

근거 자체는 틀리지 않았다 — 저장 버튼 하나로 다섯 칸을 받는 화면이라면 맞는 말이다.
그런데 즉시 저장으로 바뀌면 같은 문장이 정확히 반대 결론을 가리킨다. 주석은 판단의
**결론**만 적고 있었고 **전제**는 안 적혀 있어서, 전제가 바뀐 걸 알아챌 방법이 없었다.

**교훈: 판단을 주석으로 남길 때는 결론이 아니라 전제를 적는다.**
「A로 한다」가 아니라 「B라서 A로 한다」. 그래야 B가 바뀐 날 A를 다시 볼 수 있다.

두 경우 다 주석을 지웠으면 오히려 빨리 찾았을 것이다 — 설명 없는 빈 catch는 의심을
사지만, 그럴듯한 설명이 붙은 빈 catch는 읽고 넘어간다.

# 부록 — 미룬 일: 초대 코드 재발급

지금 상태:

```sql
invite_code text not null unique
  default upper(substring(md5(random()::text), 1, 8))
```

8자리 고정, **만료 없음, 재발급 경로 없음.** 나간 멤버도 계속 쓸 수 있고
카톡방에 뿌려진 링크는 영원히 산다.

**검증(2026-08 시점, 동호회 3곳)에서는 만들지 않는다.** 코드는 총무가 아는
사람에게만 보내고, 나간 멤버가 재가입하면 멤버 목록에 떠서 바로 알아챈다.
지금 실제로 발생할 위험이 아니다.

## 견적

코드는 `teams` 한 칸이라 갱신 자체는 UPDATE 한 줄이다. 어려운 건 그다음이다.

| 일 | 규모 |
|---|---|
| 재발급 RPC (`is_team_admin` 확인 + 새 코드) | SQL 15줄 |
| 시트에 「코드 재발급」 — QR 바로 아래 | 작음 |
| 확인 대화상자 「보낸 링크와 QR이 모두 무효가 돼요」 | 작음 |
| **충돌 재시도** — `unique` 컬럼이라 md5 8자리가 겹치면 23505. 루프 필요 | 중간 |
| `invite-redirect`에 「만료된 초대예요」 | 작음 |

**승인 기능과 달리 RLS를 안 건드린다.** `teams` 한 칸 UPDATE고 `is_team_admin`은
이미 있다. 그게 결정적인 차이다 — 체감 규모는 F-1 + F-2를 합친 것보다 조금 작다.

## 자리는 이미 만들어뒀다

버튼은 **초대 시트 안, QR 바로 아래**여야 한다. 다른 화면에 두면 총무가 방금
대면으로 보여준 QR이 죽은 걸 모른다. 같은 화면에서 눌러야 「이 그림이 지금
바뀐다」가 보인다. InviteSheet가 그 자리다.

## 열려 있는 설계 갈림길 — 유예

재발급은 「이전 코드 즉시 사망」인데, 총무가 카톡방에 링크를 뿌려둔 상태에서
누르면 아직 안 들어온 사람들이 전부 막힌다. 유예(구 코드 24시간 유지)를 두려면
컬럼이 하나 더 필요하고(`prev_invite_code` + 만료 시각) 규모가 두 배쯤 된다.

**지금은 판단 근거가 없다.** 즉시 사망이 실제로 문제가 되는지는 총무가 코드를
어떻게 뿌리는지 봐야 안다. 4주 검증하면 답이 나온다. 근거 없이 유예를 만들면
「왜 옛날 링크가 아직 되지?」라는 다른 혼란을 만든다.
