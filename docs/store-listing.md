# Play 스토어 등록 정보 — 초안

⚠ **초안이다. 문구는 사용자가 고친다.** 여기 적힌 기능은 전부 실제로 도는 것만 골랐다 —
스토어 문구가 앱보다 앞서가면 리뷰에서 걸리고, 걸리지 않아도 첫 리뷰가 나빠진다.

---

## 짧은 설명 (80자)

```
풋살 모임의 참석 투표부터 회비 정산까지. 총무의 반복 작업을 앱이 대신합니다.
```

**44자.** 여유가 있어 다른 안도 적어 둔다:

| 안 | 문구 | 자수 |
|---|---|---|
| A ⭐ | 풋살 모임의 참석 투표부터 회비 정산까지. 총무의 반복 작업을 앱이 대신합니다. | 44 |
| B | 참석 투표 · 회비 정산 · 팀 분배까지. 풋살 모임 총무를 위한 앱. | 39 |
| C | 매주 카톡으로 하던 참석 확인과 회비 정산, 이제 앱에서 한 번에. | 36 |

⚠ A를 권한다. **누구를 위한 앱인지**(총무)와 **무엇을 대신하는지**(반복 작업)가 둘 다 들어간다.
B는 기능 나열이라 스크린샷과 겹치고, C는 「카톡」이 남의 상표다 — 규정 위반은 아니지만
비교 광고로 읽힐 여지를 만들 이유가 없다.

## 긴 설명 (4000자)

```
풋살 모임을 굴리는 사람은 매주 같은 일을 반복합니다.
누가 오는지 묻고, 인원을 세고, 구장비를 나누고, 안 낸 사람에게 다시 말합니다.
KickDay는 그 반복을 대신합니다.


■ 참석 투표

경기를 만들면 팀원에게 알림이 갑니다. 참석·불참·미정 중에 고르면 끝입니다.
정원을 넘으면 자동으로 대기자가 되고, 앞사람이 빠지면 순서가 올라갑니다.
아직 안 고른 사람에게는 총무가 독촉 알림을 보낼 수 있습니다.

투표 마감을 정해두면 그 시각에 잠깁니다. 마감 뒤에는 명단이 바뀌지 않아
구장에 몇 명이 오는지 그대로 믿을 수 있습니다.


■ 회비 정산

경기가 끝나면 총 금액만 넣으세요. 1인당 금액은 참석자 수로 나눠 계산합니다.
사정이 있는 사람은 정산 대상에서 빼면 나머지 금액이 다시 계산됩니다.

팀원은 자기 몫을 보고 바로 송금할 수 있습니다.
토스·카카오뱅크·KB·신한은 계좌와 금액이 채워진 화면으로 바로 넘어가고,
앱이 없으면 계좌번호를 복사합니다.
송금하고 돌아오면 「입금했어요」를 묻고, 총무가 확인하면 완납으로 바뀝니다.

누가 냈고 누가 안 냈는지 한 화면에서 보입니다. 미입금자에게만 알림을 보낼 수 있습니다.


■ 경기 운영

경기 중에는 타이머와 스코어보드를 씁니다.
쿼터 시간을 정하고, 추가시간을 더하고, 점수를 올립니다.
경기가 끝나면 그대로 정산으로 이어집니다.

참석자를 실력과 포지션으로 나눠 팀을 짜는 기능도 있습니다.
피보·알라·픽소·골레이로를 반영해 양 팀의 균형을 맞춥니다.


■ 팀

초대 코드나 링크 하나로 팀원을 부릅니다.
공지사항과 게시판으로 이야기하고, 댓글에서 @로 사람을 부를 수 있습니다.
투표(폴)로 「이번 주 언제 할까요」 같은 것을 정합니다.

멤버마다 주발·포지션·등번호·실력을 둘 수 있고,
실력은 총무만 매깁니다 — 팀 분배가 그 값을 쓰기 때문입니다.


■ 알림

새 경기, 투표 마감, 우천 안내, 공지, 댓글, 멘션, 회비 독촉.
어떤 알림을 받을지는 종류별로 끌 수 있습니다.
알림을 누르면 그 경기의 날짜, 그 정산으로 곧장 열립니다.


■ 화면

어두운 모드와 밝은 모드를 모두 지원합니다. 기기 설정을 따라가게 둘 수도 있습니다.
스크린리더로도 쓸 수 있게 버튼마다 무엇인지, 지금 어떤 상태인지 읽어줍니다.


■ 이런 분께

· 매주 풋살 모임을 여는 총무
· 참석 확인이 채팅방에서 흩어지는 팀
· 회비를 누가 냈는지 따로 적어두고 있는 팀
· 구장비를 매번 계산기로 나누는 팀


KickDay는 광고가 없습니다.
```

**1,244자.** 상한(4000)에 여유가 많다.

### 감사 — 나중에 거짓이 될 문장이 있는가

지목된 셋은 **전부 깨끗하다.** 낱말로 훑어 확인했다:

  무료 0 · 아이폰/iOS/애플 0 · 예약 0 · 전적/순위/랭킹/통계 0

| | 문장 | 판정 |
|---|---|---|
| ⚠ **1** | 「KickDay는 광고가 없습니다」 | **지금은 사실.** 수익화를 넣으면 거짓이 된다. 구독을 검토 중이므로 넣을 거면 그때 이 줄부터 지워야 한다 |
| ⚠ **2** | 「알림을 누르면 그 경기의 날짜, 그 정산으로 곧장 열립니다」 | **앱은 준비됐고 서버가 아직이다.** 딥링크 1단계는 끝났지만(`58264b9`) `notify-team` Edge Function을 **배포해야** 알림에 목적지가 실린다. 배포 전에는 이 문장이 거짓이다 |
| ⚠ **3** | 「총무가 독촉 알림을 보낼 수 있습니다」 | **코드로는 오늘 이어졌다**(`9b21349`). 그전까지 한 번도 안 갔다. **기기에서 도착을 아직 못 봤다** — 계정 둘이 필요하다(서랍 「확인 필요」 1-c) |
| ⚠ **4** | 「어떤 알림을 받을지는 **종류별로** 끌 수 있습니다」 | **살짝 과하다.** 종류는 여덟인데 스위치는 **넷**이다(경기 · 공지 · 게시판 · 정산). 「종류별로」 → 「경기·공지·게시판·회비로 나눠서」가 정확하다 |
| | 「정원을 넘으면 자동으로 대기자가 되고, 앞사람이 빠지면 순서가 올라갑니다」 | **사실.** `capacity.ts`가 매번 다시 계산한다(저장된 상태가 아니다) |
| | 「어두운 모드와 밝은 모드를 모두 지원합니다」 | **사실.** `palettes` · `themeStore` · 설정 > 화면 모드 |
| | 「스크린리더로도 … 읽어줍니다」 | **사실.** role 없는 Pressable 0곳. 다만 TalkBack으로 처음부터 끝까지 써 본 적은 없다 |

⚠ **2와 3이 같은 성격이다** — 코드가 맞아도 **한 단계가 남아 있다.**
  2는 배포, 3은 기기 확인. 스토어 문구는 사용자가 설치한 앱 기준이라
  **둘 다 끝난 뒤에 올려야** 거짓이 아니다.

⚠ 「팀 분배」는 균형을 맞춘다고만 적었다. 어떻게 맞추는지(점수 합)는 안 적었다 —
알고리즘을 문구로 약속하면 나중에 바꾸기 어렵다.

## 스크린샷 — 아직 안 찍은 이유와 계획

### ⚠ 지금 찍지 않는다

**실기기 확인(서랍 「확인 필요」 1번)을 먼저 한다.** 그라데이션 밴딩이 실기기에서
보이면 배경을 걷어내야 하는데, 그건 **모든 화면의 배경**이라 전부 다시 찍는다.
스크린샷은 출시 직전에 필요한 자산이라 지금 찍어 둘 이득이 없다.

반대로 **밴딩과 무관해서 지금 해도 낭비가 없는 것**은 먼저 했다 —
아이콘, 피처 그래픽, 문구. 데이터 픽스처도 여기 든다(그림이 아니라 데이터다).

### ⚠ 지금 데이터로는 못 찍는다

에뮬레이터의 지금 상태를 이번 세션에 여러 번 떴다:

  이번주 경기    「예정된 경기가 없습니다」
  공지          「aa」 · 「aaaa」 · 「asda」
  이번 달 참석률  「-」
  팀원          1명
  정산          5건인데 4건이 「미등록」

**앱이 비어 보이고 고장 나 보인다.** 스크린샷 첫 장이 「예정된 경기가 없습니다」면
설치 안 한다.

### 실제 데이터로는 못 채운다

참석률·명단·팀 분배·정산 진행률은 **팀원이 여럿이어야** 그럴듯해진다.
계정이 하나뿐이라 실제로는 못 만든다. 프로덕션 DB에 가짜 팀을 넣는 것도 안 한다.

**픽스처로 간다 — `src/dev/screenshotFixtures.ts`. 만들었다.**

  팀        강남 FC · 「수요일 저녁, 강남에서 뜁니다」 · 서울 강남구
  멤버      8명. 포지션 넷이 골고루, 실력 상·중·하가 섞인다
  경기      다가오는 2건(정원 6에 참석 7 → **대기 1명**, 미투표 1명 → 독촉이 산다)
            지난 4건 — 있어야 참석률이 「-」가 아니라 숫자로 나온다
  정산      진행 1건. 7명 × 9,000원, 셋이 미납이고 그중 하나는 「확인 대기」.
            미등록 1건도 둔다 — 정산 탭의 두 갈래가 다 보여야 한다
  공지      3건, 하나 고정. 「9월 회비 안내」·「수요일 구장이 A구장으로 바뀝니다」
  투표      「다음 달 정기전, 어느 요일이 좋으세요?」 응답 4

⚠ **로더도 같이 갈아 끼운다.** 값만 넣으면 화면이 마운트될 때 `loadMatches()`가
  돌아 빈 데이터로 덮어쓴다. Zustand는 함수도 상태라 `loadMatches: NOOP`으로 막는다.

⚠ **게시글·댓글은 안 넣었다.** 스토어가 아니라 `BoardPanel`의 지역 상태다
  (`useState` + `fetchPosts`). 넣으려면 서비스에 분기를 만들어야 하는데,
  그건 **릴리스 코드에 픽스처가 닿는 자리를 새로 만드는 일**이라 이 파일이
  피하려는 바로 그것이다. 여덟 장에 게시판이 없으므로 지금은 안 넣는다.
  넣기로 하면 서비스에 「대체 함수 슬롯」을 두고 이 파일이 등록하는 방식이 맞다.

### 켜고 끄는 법

    EXPO_PUBLIC_SCREENSHOT=1 npx expo start --dev-client

가드가 셋이고 셋 다 있어야 돈다. `screenshot.check.ts`가 넷을 붙든다:

  ① 픽스처 안에서 `__DEV__`와 환경변수를 **둘 다** 본다 (부르는 쪽을 안 믿는다)
  ② `setState`가 가드 **뒤에** 온다 (앞이면 가드가 무의미하다)
  ③ 부르는 자리가 `App.tsx` 하나뿐이다 — `src/` 안에서 부르면 실패한다
  ④ 픽스처가 supabase도 fetch도 안 쓴다 (스토어에 넣는 것까지다)
  ⑤ 「테스트1」·「asdf」 같은 임시 문구가 없다

⚠ `__DEV__` 하나로 안 끝낸 이유: 개발 빌드로 시연하다 켜진 채 남는 경로가 있다.
  환경변수를 따로 두면 **켜는 것이 언제나 의도적인 일**이 된다.

### 어느 화면을 넣을까 — 제안

처음 보는 사람에게 **무엇을 해결하는 앱인지**를 순서로 말한다.
기능 나열이 아니라 「총무의 하루」 순서다.

| # | 화면 | 왜 이 자리인가 | 자막(스크린샷 위 문구) |
|---|---|---|---|
| **1** | 홈 — 다음 경기 D-day·참석 링·미납 한 줄 | 첫 장이 앱 전체를 말해야 한다. **지금 뭘 해야 하는지**가 한 화면에 있다 | 이번 주 경기, 한눈에 |
| **2** | 명단 시트 — 참석/불참/미정 탭 + 미투표 독촉 | 가장 자주 쓰는 기능이고 경쟁 앱과 갈리는 자리다 | 누가 오는지 묻지 않아도 됩니다 |
| **3** | 정산 상세 — 1인당 금액·입금 현황·송금 버튼 | **돈이 이 앱의 이유다.** 여기서 설치가 갈린다 | 구장비, 나누는 것부터 받는 것까지 |
| **4** | 송금 시트 — 토스·카뱅·KB·신한 | 3의 증거. 「진짜 되는구나」가 여기서 온다 | 계좌와 금액까지 채워서 |
| **5** | 경기 운영 — 타이머·스코어보드 | 경기 당일에도 쓴다는 것 | 경기 중에도 |
| **6** | 팀 분배 — 포지션별 두 팀 | 「이런 것까지」의 자리 | 실력과 포지션으로 팀 짜기 |
| **7** | 밝은 모드 홈 | 어두운 화면만 일곱 장이면 앱이 어둡기만 한 줄 안다.<br>⚠ 「다크 고정 아니냐」는 지적이 있었는데 **밝은 모드는 있다** — `theme.ts:286` `lightColors` · `palettes` · 설정의 「화면 모드」 · `themeStore`. 이번 세션에 넣고 216곳 색을 옮겼다.<br>다만 `app.json`의 `userInterfaceStyle: "dark"`는 **네이티브 기본값**이라 그 줄만 보면 고정으로 읽힌다 — 실행 중에는 themeStore가 덮는다 | 밝은 모드도 |
| **8** | 알림 설정 | 광고 앱이 아니라는 신호 | 받을 알림은 직접 고릅니다 |

⚠ **1~4가 핵심이다.** Play는 목록에서 앞 2~3장만 보인다.
  5~8은 상세로 들어온 사람용이라 없어도 되지만, 있으면 완성도로 읽힌다.

⚠ 자막을 넣을지는 정해야 한다. 넣으면 만드는 품이 들고(합성 스크립트가 필요하다)
  번역이 생기면 그만큼 늘어난다. **1~4만 자막을 넣고 5~8은 맨 화면으로 두는 것**을 권한다.

### 규격

  폰      1080×2400 (에뮬레이터 그대로). Play는 320~3840px, 9:16~16:9면 받는다
  형식    PNG 또는 JPEG, 24비트, 알파 없음
  ⚠ 상태바의 시계·배터리는 그대로 둔다. 지우면 오히려 어색하고 규정이 요구하지도 않는다
  ⚠ **개발 클라이언트 배너가 안 뜨는지 본다.** dev client로 찍으면 위에 띠가 남는다 —

## 데이터 안전(Data safety) — 초안

⚠ **초안이다.** 근거는 `src/features/auth/terms.ts`(개인정보 처리방침)와 실제 스키마·엔드포인트다.
그 파일 머리에 「법률 검토 전 초안」이라 적혀 있고, 여기도 같다.

⚠ Play 양식은 항목마다 **수집(collected)** 과 **공유(shared)** 를 따로 묻는다.
  · 수집 = 기기 밖으로 나간다
  · 공유 = 제3자에게 넘어간다 (서비스 제공자 위탁은 보통 「공유」에서 뺀다)

### 수집 항목

| Play 분류 | 항목 | 수집 | 공유 | 목적 | 필수 | 근거 |
|---|---|---|---|---|---|---|
| Personal info → Name | 이름(닉네임) | ✔ | ✖ | 앱 기능 | **필수** | 팀원 명단에 보이는 이름 |
| Personal info → Email address | 이메일 | ✔ | ✖ | 앱 기능 · 계정 관리 | **필수** | 로그인 식별자 |
| Personal info → User IDs | 계정 고유 id, 소셜 제공사 식별자 | ✔ | ✖ | 계정 관리 | **필수** | |
| Photos and videos → Photos | 프로필 사진 | ✔ | ✖ | 앱 기능 | 선택 | 안 올려도 쓴다 |
| **Financial info → Other financial info** | **은행명 · 계좌번호 · 예금주** | ✔ | ✖ | 앱 기능 | 선택 | ⚠ **총무만** 등록한다. 팀원 계좌는 수집하지 않는다 |
| Location → Approximate location | 구장 검색 시 현재 위치 | **판단 필요** | 카카오 | 앱 기능 | 선택 | 아래 ⚠ |
| Messages → Other in-app messages | 공지 · 게시글 · 댓글 | ✔ | ✖ | 앱 기능 | 선택 | |
| App activity → Other actions | 참석 응답 · 팀 분배 결과 · 정산 금액/입금 여부 | ✔ | ✖ | 앱 기능 | **필수** | 앱의 본체다 |
| Device or other IDs | 푸시 알림 토큰 | ✔ | **Expo** | 앱 기능(알림) | 선택 | 알림을 끄면 안 쓴다 |
| App info and performance | **없음** | ✖ | ✖ | | | 광고 식별자·분석 도구를 안 쓴다 |

### ⚠ 위치 — 「수집」으로 신고할지 정해야 한다

구장을 검색할 때만 단말 위치를 쓰고 **저장하지 않는다.** 카카오 API 약관이
검색 결과 저장을 금지해서 실시간 호출만 한다.

Play에는 **일시 처리(ephemeral) 예외**가 있다 — 메모리에서만 쓰고 저장하지 않으면
「수집 안 함」으로 신고할 수 있다. 다만 좌표가 **카카오로 나가는 것은 사실**이다.

  안전한 쪽   「수집함 · 공유함(카카오)」으로 신고한다. 설명이 길어지지만 반박당하지 않는다
  좁은 쪽     일시 처리 예외로 「수집 안 함」. 대신 카카오를 서비스 제공자로 볼 수 있어야 한다

⚠ **안전한 쪽을 권한다.** 위치는 리뷰가 특히 깐깐하고, 틀리면 앱이 내려간다.
  얻는 것(「위치 수집 안 함」 배지)보다 잃는 것이 크다.

### 보안

| 질문 | 답 | 근거 |
|---|---|---|
| 전송 중 암호화하는가 | **예** | Supabase·Expo·카카오·기상청 모두 HTTPS. 평문 엔드포인트가 없다 |
| 저장 시 암호화하는가 | **예**(위탁사 기준) | Supabase가 저장 암호화를 한다. 비밀번호는 앱도 운영자도 원문을 못 본다 |
| 데이터 삭제를 요청할 수 있는가 | **예** | 설정 > 회원 탈퇴. 탈퇴 시 회원 정보를 지체 없이 파기한다 |
| 데이터 수집이 필수인가 | **일부만** | 참석·정산은 필수, 사진·계좌·위치·알림은 선택 |

### 보관 기간 (처리방침과 같아야 한다)

  회원 정보    탈퇴 시 지체 없이 파기
  정산 기록    정산 완료 후 **3년** — 팀 내 회비 분쟁의 확인 근거
  접속 기록    **3개월** (통신비밀보호법)

⚠ **정산 기록 3년은 「탈퇴하면 다 지운다」와 어긋나 보인다.** 실제로는 탈퇴해도
  남는 값이 있다는 뜻이므로, Play 양식의 「삭제 요청 가능」과 함께 읽히면
  모순으로 보인다. 처리방침에 이유가 적혀 있으니 문구를 맞춰 두는 게 안전하다.

### ⚠ 출시 전에 반드시 채워야 하는 것

| | 무엇 | 지금 값 |
|---|---|---|
| **1** | 약관 시행일 | `EFFECTIVE_DATE = '[시행일]'` — **플레이스홀더 그대로다** |
| **2** | 계정 삭제 **웹 페이지** | 없다. Play는 앱 밖에서도 삭제를 요청할 URL을 요구한다 |
| **3** | 개인정보 처리방침 **공개 URL** | 앱 안에만 있다. Play 등록에는 웹 URL이 필요하다 |
| **4** | 법률 검토 | `terms.ts` 머리에 「검토 전 초안」이라 적혀 있다. 보유 기간과 Supabase 국외 접근 여부가 미확인이다 |

⚠ 2와 3은 `kickday.app` 도메인이 이미 있으니 정적 페이지 두 장이면 된다.
  `build-web-terms.mjs`가 이미 약관을 웹으로 뽑고 있으므로 그 출력을 올리면 3은 끝난다.
