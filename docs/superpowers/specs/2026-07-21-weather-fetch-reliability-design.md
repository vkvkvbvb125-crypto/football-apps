# 날씨 조회 신뢰성 개선 설계

## 배경

날씨 조회가 가끔 500 에러로 실패하는 문제를 조사한 결과, 진짜 원인은 다음 조합으로 확인됨:

1. 화면 하나(일정 탭)를 열 때 캘린더용 날씨(최대 오늘부터 10일치)와 각 경기 카드(`WeatherBadge`)용 날씨가 **동시에** 여러 개 발사됨 (한 화면에서 최대 15개 안팎).
2. 기상청 공공데이터포털 API는 같은 인증키로 짧은 시간에 여러 요청이 몰리면 응답을 거부/실패하는 경우가 있음 (공공데이터포털 API의 일반적인 특성).
3. AWS Lambda 릴레이(`weather-kma-relay`)는 이 실패를 감지해서 자체적으로 502를 정상 반환함 (Lambda 자체는 크래시 없이 잘 끝남 — CloudWatch에 실패로 안 잡히는 이유).
4. 하지만 Supabase 엣지함수(`fetch-weather/index.ts`)의 `fetchViaRelay`는 릴레이가 non-2xx를 반환하면 무조건 `throw`로 예외를 던지고, 이 예외를 잡는 코드가 없어서 엣지함수 전체가 처리되지 않은 예외로 죽어 클라이언트에 500이 감.

목표는 "실패해도 예쁘게 보여주기"가 아니라 **애초에 덜 실패하게 만드는 것**. 아래 세 가지를 함께 적용한다.

## 목표

1. 한 화면에서 나가는 날씨 조회 요청의 동시 실행 개수를 제한해서, 기상청 API에 요청이 몰리는 상황 자체를 줄인다.
2. 그래도 일시적으로 실패하면(네트워크 hiccup, 기상청 API 일시 오류) 클라이언트에서 짧게 기다렸다가 자동으로 재시도한다.
3. 엣지함수는 릴레이 호출이 실패해도 500으로 죽지 않고, 기존의 다른 "조회 불가" 케이스들처럼 `available: false`로 부드럽게 응답한다 (최후의 안전장치).

## 설계

### 1. 클라이언트: 동시성 제한 + 재시도 (`weatherService.ts`)

`fetchMatchWeather`를 호출하는 곳은 두 군데 — 캘린더의 날씨 계산 useEffect(최대 11개를 `Promise.all`로 동시 발사)와, 경기 카드마다 있는 `WeatherBadge`(각자 독립적으로 마운트 시 호출). 이 두 호출부를 각각 수정하는 대신, **`weatherService.ts` 안에 모듈 레벨 동시성 큐를 하나 두고 `fetchMatchWeather` 자체가 그 큐를 거치도록** 만든다. 이러면 호출부 코드(`AttendanceScreen.tsx`, `WeatherBadge.tsx`)는 전혀 안 건드려도 되고, 모든 날씨 조회가 자동으로 동시 3개까지만 실제 네트워크로 나가고 나머지는 대기열에서 순서를 기다린다.

재시도는 같은 함수 안에서: 실패하면 500ms, 1000ms 간격으로 최대 2번 더 시도(총 3번 시도), 그래도 실패하면 기존처럼 에러를 던져서 `WeatherBadge`가 "날씨 조회가 안 되는 날짜예요"로 처리하게 둔다(최후의 표시).

### 2. 엣지함수: 릴레이 실패를 우아하게 처리 (`fetch-weather/index.ts`)

`fetchViaRelay`가 실패해도(릴레이 호출 자체가 non-2xx, 또는 네트워크 예외) 엣지함수가 통째로 죽지 않도록, 이 함수를 호출하는 두 지점(단기예보 분기, 중기예보의 `fetchMidForecast` 내부)에서 실패를 잡아 `available: false, reason: 'relay_failed'`로 응답하게 한다.

### 3. 진단용 디버그 필드는 유지

지난번에 추가한 `reason`/`midDebug`/`availableSlots` 같은 디버그 필드들은 클라이언트가 어차피 `available`만 보고 나머지는 무시하므로 그대로 둔다 — 나중에 비슷한 문제가 또 생기면 바로 원인 파악에 쓸 수 있다.

## 검증 방법

테스트 프레임워크가 없으므로 `npx tsc --noEmit` + 수동 확인으로 검증한다. 수동 확인 시나리오:
1. 일정 탭을 열었을 때 Network 탭에서 `fetch-weather` 요청이 3개씩 순차적으로 나가는지(한꺼번에 10개 이상 동시에 나가지 않는지)
2. 이전에 실패했던 경기(예: 7/21, 7/22)들의 날씨가 이제 안정적으로 뜨는지 여러 번 새로고침해서 확인
3. 의도적으로 실패를 재현하기 어려우므로, 재시도 로직 자체는 코드 리뷰로 확인 (실제 기상청 API가 자주 실패하지 않는 이상 재시도가 실제로 도는 걸 보긴 어려움)
